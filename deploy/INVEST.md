# Обновление существующего api.m1917.kz на Invest

На Invest уже работают Nginx/TLS и `m1917-backend.service`, старый код расположен в `/opt/m1917-backend`, настройки — `/etc/m1917/backend.env`. Новый код выкладывается отдельно в `/srv/alash`. Не используйте генератор новых ключей для этой базы: нужно сохранить действующий PII/JWT и остальные настройки.

Порядок установки:

1. Получить ветку codex/backend-server в отдельный каталог, собрать Backend Docker image (ffprobe уже внутри).
2. Запустить `deploy/prepare_existing.py prepare` через Python3.12+ окружения приложения с PID действующего сервиса. Скрипт сохраняет приватную нормализованную environment-копию, финансовый read-only fingerprint и зашифрованный PostgreSQL custom dump. Проверяет расшифровку и `pg_restore --list`. Все файлы остаются в закрытом каталоге сервера.
3. В новом image с `--network host` и `/etc/m1917/backend.codex.env` выполнить `alembic upgrade head`. Текущая конечная ревизия — `20261106_0049`, объединяющая новые функции и изображения новостей; исходные финансовые суммы не переписываются.
4. `prepare_existing.py verify` сравнивает прежние финансовые поля/количество строк/хеши после миграций. При расхождении не переключать трафик, выяснить причину (включая возможные параллельные действия пользователей).
5. Проверить кандидат на127.0.0.1:8017: /health/ready, schema contract/OpenAPI, отказ без токена.
6. Сохранить текущую systemd unit и drop-ins, установить `m1917-backend.docker.conf` как отдельный drop-in для того же сервиса и перезапустить только `m1917-backend`. Nginx продолжает направлять api.m1917.kz на127.0.0.1:8000. Другие проекты сервера не изменяются.
7. Проверить HTTPS /health/ready и API. При ошибке запуска удалить только новый drop-in, daemon-reload и запустить исходный сервис из `/opt/m1917-backend`. Автоматически восстанавливать/перезаписывать рабочую БД нельзя; encrypted dump — аварийная точка восстановления, не команда на потерю новых данных.

Финансовый fingerprint включает только идентификаторы, суммы, валюты, даты, статусы и связи; паспортов/банков/имён в нём нет. Реальный read-only reconciliation report хранится приватно, не публикуется в GitHub. Местный backup не заменяет независимую off-host систему резервного копирования.

Для последующих обновлений уже работающего Docker-сервиса из `/srv/alash`:

```bash
cd /srv/alash
git pull --ff-only origin codex/backend-server
bash deploy/update_existing.sh
```

Запускайте от root. Скрипт использует существующие `/etc/m1917/backend.codex.env`,
`/opt/m1917-backend/.venv/bin/python`, `/usr/bin/pg_dump` и `/usr/bin/pg_restore`.
Он сохраняет старый образ под отдельным тегом, собирает новый и проверяет маршруты,
создаёт и проверяет зашифрованный backup в `/var/backups/m1917`, останавливает сервис
на время миграций и сверки финансовых данных, затем проверяет `/health/ready`.
Рабочий env-файл не заменяется, seed-команды не запускаются. Если после backup и
до остановки были параллельные изменения финансовых данных, сверка может остановить
обновление: изучите причину, не обходите проверку автоматически.
При ошибке скрипт пытается вернуть прежний runtime-образ и запустить сервис;
база данных автоматически не откатывается. Миграции остаются применёнными.

Приложение использует `https://api.m1917.kz/api/v1`; WebSocket — тот же домен с wss. Для текущих Flutter-исходников адрес меняется `API_BASE_URL`. Не включайте фоновые прогулы задним числом: worker требует согласованную дату и утверждённый календарь.
