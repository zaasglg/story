# ALASH M-1917 API

FastAPI modular backend for the ALASH M-1917 workforce platform. The identity foundation uses PostgreSQL, Redis rate limiting, salted scrypt password hashes, short-lived JWT access tokens, rotating opaque refresh tokens, and explicit server-side role permissions.

Use the repository root `README.md` for startup and verification commands. Configuration is loaded from `M1917_*` environment variables; public authentication payloads never accept a role.

### Выбор адреса на карте

В форме объекта кнопка «Выбрать на карте» открывает поиск и выбор точки.
Адрес и координаты сохраняются после сохранения формы. Ручная замена адреса
очищает прежние координаты. Старые объекты могут оставаться без координат.

API `/api/v1/admin/maps/config`, `/search`, `/reverse` доступен администратору.
По умолчанию используются тайлы OpenStreetMap и поиск Photon; требуется интернет.
Результаты кешируются на сутки в Redis, обращения к геокодеру ограничены
общим интервалом 1,1 секунды. Поиск запускается при отправке запроса.
Для своей инфраструктуры задайте `M1917_GEOCODING_URL` (Photon API),
`M1917_MAP_TILE_URL` (шаблон `{z}/{x}/{y}`), `M1917_MAP_ATTRIBUTION` и
`M1917_MAP_ATTRIBUTION_URL`. Для большой нагрузки используйте свой Photon
или совместимый сервис вместо публичного демонстрационного сервера.

### Зарплатный счёт работника

В карточке сотрудника руководитель добавляет банк, IBAN и ФИО владельца.
`GET /api/v1/admin/workers/{id}/salary-account`, `PUT` и `DELETE` доступны
только руководителю. Администратор, мастер и работник
не имеют доступа к этим маршрутам. IBAN проверяется по формату и контрольным
цифрам, пробелы удаляются. Реквизиты хранятся одним зашифрованным значением
в `employee_private_data` с ключом `M1917_PII_ENCRYPTION_KEY`; журнал аудита
содержит факт просмотра/изменения без реквизитов. Существующие сотрудники
изначально не имеют зарплатного счёта. В интерфейсе IBAN скрыт по умолчанию.

### Личные банковские счета руководителя

`/api/v1/boss/personal-bank-accounts` поддерживает GET/POST и PUT/DELETE по ID.
Разрешение `personal_bank:manage:own` назначено только роли BOSS. Все запросы
ограничены текущим владельцем: другой руководитель не получает чужие счета,
а ADMIN, MASTER и WORKER получают 403. Поля: `name`, `bank_name`, `iban`,
`account_holder`; IBAN нормализуется и проверяется по контрольным цифрам.
Все реквизиты, включая название счёта, зашифрованы в отдельной таблице
`personal_bank_accounts`. Аудит содержит только факт операции и ID.
Счета компании по-прежнему находятся в `/boss/bank-accounts`; личные счета
не попадают в этот список и финансовые сводки компании. Выручка, прибыль,
общая финансовая сводка и счета компании доступны только руководителю;
администратор создаёт заявки на начисления и выплаты, но не видит расходы компании.

### Изменение уже начисленной зарплаты

Администратор видит начисления в `GET /admin/salary-ledger` (limit/offset, поиск q).
`POST /admin/salary-ledger/{id}/change-requests` с `Idempotency-Key` принимает
`expected_amount`, `expected_revision`, `new_amount`, `reason` и создаёт заявку
SALARY_CHANGE в статусе PENDING_BOSS. Новая сумма не применяется до решения.
Для одного начисления допускается одна ожидающая заявка. Валюта, сотрудник и
месяц берутся из исходного начисления, а не из запроса клиента.

Руководитель получает уведомление и рассматривает заявку в существующем разделе
«Согласование выплат» через `/boss/approvals/{id}/approve` или `/reject`.
Одобрение атомарно добавляет LedgerCorrection; исходное начисление сохраняется.
Повторное одобрение не создаёт дубль. Проверяются сумма и ревизия, поэтому
устаревшую заявку нельзя применить даже после возврата суммы к прежнему значению.
Отклонение и отмена сохраняют действующую зарплату. Нулевая сумма означает
отмену начисления после одобрения и также сохраняет историю. Решение приходит
уведомлением создавшему заявку администратору. Push содержит только общий
сигнал; подробности доступны после входа в приложение.

Миграция 0026 расширяет финансовые заявки. Обратная миграция отказывается
удалять новую схему, если уже существует история SALARY_CHANGE.

### Бонусы, штрафы и авансы

Администратор создаёт BONUS, PENALTY или ADVANCE через финансовую заявку.
Сумма всегда положительная, а тип определяет её влияние: бонус увеличивает
начисление, штраф уменьшает начисление, аванс уменьшает остаток к выплате.
До одобрения BOSS заявка PENDING_BOSS не попадает в реестр, сводки и историю
подтверждённых операций работника. REJECTED и CANCELLED также не учитываются.
Повторное одобрение не создаёт второй записи. Администратор, мастер и работник
не могут одобрять заявки или передать статус APPROVED при создании.

Создание заявки формирует уведомления активным руководителям в той же транзакции.
Решение формирует уведомление создавшему заявку администратору. Повтор отправки
с тем же Idempotency-Key и повторное одобрение не дублируют уведомления.

### Финансы объекта по месяцам

Руководителю доступен переход «Объекты → город → объект». Отчёт использует
`GET /boss/finance/object/{id}?date_from=YYYY-MM-01&date_to=YYYY-MM-DD`, где
последняя дата — последний календарный день выбранного месяца. Доход, расходы
и чистая прибыль считаются только по подтверждённым неархивным операциям,
явно привязанным к этому объекту; валюты показываются отдельными блоками.
`GET /boss/finance/object/{id}/months` возвращает месяцы с такими операциями
в обратном порядке, включая месяцы только с расходами. По умолчанию экран
открывает последний месяц с данными; можно выбрать другой месяц или год.
Оба маршрута требуют PROFIT_READ и недоступны администратору, мастеру и работнику.

Месячные финансовые отчёты руководителя возвращают `expense_breakdown` — суммы подтверждённых расходов по категориям отдельно для каждой валюты. Их сумма совпадает с `approved_expenses`. Доходы и прибыль доступны только роли BOSS; администратор не имеет доступа к расходам и этим отчётам. Зарплатные начисления учитываются в расходах только после регистрации и подтверждения соответствующего расхода, без автоматического дублирования начислений.

Итоговая матрица доступа (скриншот пользователя): ADMIN не получает EXPENSE_READ/EXPENSE_MANAGE и доступ к банковским счетам. Расходами и банковскими счетами работников управляет BOSS. MASTER ограничен своей командой, в том числе публичные карточки и фотографии. Журнал `/admin/audit` содержит только собственные действия, `/boss/audit` — действия администраторов; секретные значения не выдаются. Изменения зарплаты, бонусы, штрафы и авансы по-прежнему требуют одобрения BOSS.

### Голосовые сообщения

`POST /chats/{thread_id}/voice` принимает multipart: `client_message_id`, `duration_ms` (500–300000) и `file` (до 5 МБ, M4A/WebM/Ogg). Отправка атомарная и идемпотентная; повтор с изменённым содержимым возвращает 409. Аудио хранится в PostgreSQL (миграция 0027). История содержит защищённый `voice_url`, MIME и длительность; сами байты выдаются отдельным GET только участникам переписки. Публичных ссылок нет. Текстовые сообщения работают как прежде.

### Администраторы

Только руководитель (разрешение `user_role:manage`) управляет `/boss/administrators`: GET с `q`, `limit`, `offset`, POST с ФИО, телефоном и паролем. Роль задаётся сервером как ADMIN. `PUT /{id}/status` меняет ACTIVE/BLOCKED, `POST /{id}/password` устанавливает новый пароль. Эти операции не могут изменять работников, мастеров или руководителей. Блокировка, разблокировка и сброс пароля увеличивают `auth_version` и отзывают старые сеансы. Пароли не возвращаются в API и не попадают в аудит. В приложении раздел находится у руководителя в «Ещё → Администраторы».

Работник просматривает свой зарплатный счёт через `GET /workers/me/salary-account` (разрешение `worker_bank:read:own`). Владелец определяется из текущей сессии, передать ID другого работника нельзя. Маршрут не поддерживает изменение или удаление; реквизиты по-прежнему изменяет руководитель. В профиле работника IBAN скрыт по умолчанию, доступны показ и копирование.
